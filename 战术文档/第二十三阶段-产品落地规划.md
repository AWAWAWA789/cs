# 第二十三阶段 · 产品落地规划

> **战略主线**：闭合三个核心断层 + 启动一个飞轮，让"双轨交叉验证 + 越用越准"从
> 架构叙事变成产品事实。
>
> 三个断层（来自 v0.3 诊断）：
> 1. **K 线轨断层**：单品 `/info/chart` 只返回收盘价，OHLC 被伪造 → 6 项规则 4 项失效
> 2. **训练断层**：训练权重落盘了，但推理路径不消费 → "越用越准"不成立
> 3. **库存断层**：无历史库存快照 → 双轨融合无法回测、训练实为单轨
>
> 一个飞轮：分析 → 自动入案例库 → 事后标注 → 增量训练 → 推理升级

---

## 一、规划原则

1. **数据真实性优先**：宁可用更少特征，也不用伪造数据算分
2. **闭环优先于扩张**：先把现有功能跑成"真闭环"，再谈新品类/新算法
3. **最小可用增量**：每个阶段产出可独立验证的成果，避免大爆炸式发布
4. **一人可用**：所有功能以"单用户、本地优先、低运维"为前提设计

## 三、阶段 A：闭合 K 线轨断层（P0）

### A1 · 单品真实 OHLC 接入

**问题**：`/info/chart` 只返回收盘价序列，[accumulation_endpoints.py:221](file:///workspace/src/api/accumulation_endpoints.py#L221-L224) 用 `open=high=low=close` 伪造 OHLC，导致波动率/横盘/底部抬高/成交量趋势 4 项特征失真。

**方案**：

1. **接入多平台聚合**：CSQAQ `/info/chart` 支持 `platform` 参数。BUFF/悠悠/C5 平台返回粒度不同，部分平台可返回更细粒度的成交数据。优先验证哪个平台的 `/info/chart` 能给出 high/low 真实区间。
2. **回退到价格行为子集**：若所有平台都只给收盘价，则 K 线评分**降级为 3 项**（price_position / 收盘价波动率 / 收盘价横盘），不再计算 True Range ATR、不再伪造 high/low swing。
3. **数据源标记**：所有评分结果必含 `data_source` 字段，明确标注 `real_ohlc` / `close_only` / `degraded`，前端按颜色区分。

**交付物**：
- `src/api/accumulation_endpoints.py`：`_fetch_item_price_series` 增加 OHLC 真实性探测
- `src/features/accumulation.py`：新增 `add_close_only_features()` 降级特征集
- `src/scenario_engine/accumulation_detector.py`：根据数据源切换特征集
- 前端：评分卡片显示"有效特征数 X/6"与数据源徽章

**验收**：
- 同一饰品，旧版波动率分恒为 1.0，新版基于真实数据波动
- 数据源徽章可见，降级模式下特征明细只展示真实计算的项
- 单元测试覆盖 3 种数据源场景

---

### A2 · 特征工程降级策略

**问题**：现有 6 项特征权重固定，但实际只有部分生效，权重分配失真。

**方案**：

1. 定义两套特征集：
   - `FULL`（真实 OHLC）：6 项规则，原权重
   - `CLOSE_ONLY`（仅收盘价）：3 项规则（price_position / close_volatility / close_consolidation），重新分配权重
2. `rule_engine_score(features, mode="auto")` 自动按可用特征切换权重
3. 融合评分时记录 `kline_feature_mode` 字段

**验收**：
- 仅收盘价数据 → kline_score 由 3 项规则计算，不再恒高
- 训练时按 case 的 `feature_mode` 分桶训练（避免混合样本污染权重）

---

### A3 · 评分透明化

**问题**：用户无法判断当前评分可信度。

**方案**：所有评分响应增加 `confidence` 字段：
- `data_source` 真实性（real_ohlc=1.0, close_only=0.6, degraded=0.3）
- 有效特征数比例
- 样本量（案例库 <100 → 0.5，<500 → 0.7，≥500 → 0.9）
- 综合置信度 = 三项加权

**验收**：前端评分卡显示置信度条，低置信度时附提示"数据源不足，建议参考库存信号"。

---

## 四、阶段 B：闭合训练推理断层（P0）

### B1 · 训练权重接入 detect_accumulation

**问题**：[accumulation_detector.py:34](file:///workspace/src/scenario_engine/accumulation_detector.py#L34-L41) `RULE_WEIGHTS` 硬编码，`detect_accumulation` 不加载训练产物。

**方案**：

1. `detect_accumulation` 启动时调 `load_rule_weights(cache_root, category)`，若存在则覆盖 `RULE_WEIGHTS`
2. 新增 `weights_source` 字段：`trained` / `empirical`
3. 训练产物增加 `feature_mode`（FULL / CLOSE_ONLY），推理时按模式匹配权重

**交付物**：
- `accumulation_detector.py`：增加 `_resolve_weights()` 函数
- `trainer.py`：训练产物落盘 feature_mode
- 配置项 `RULE_WEIGHTS_SOURCE=auto|trained|empirical`

**验收**：
- 训练完成后，重新分析同一品，权重来源标识为 `trained`
- 删除训练产物后，自动回退 `empirical` 且无报错

---

### B2 · 在线推理路径切换

**问题**：训练闭环只在 trainer.py，detect_accumulation 不感知。

**方案**：

1. 启动时懒加载训练产物（首次调用时加载，缓存到模块级变量）
2. 训练完成后通过文件 mtime 检测刷新缓存
3. `/accumulation/analyze-fused` 与 `/accumulation/explain-fused` 响应增加 `weights_source`

**验收**：
- 训练 → 立即分析同一品 → 响应含 `weights_source: trained`
- 单元测试：mock 训练产物，验证 detect_accumulation 使用之

---

### B3 · 训练-推理一致性测试

**问题**：训练用 `FEATURE_KEYS` 10 维，推理用相同 keys 但无校验。

**方案**：新增 `tests/scenario_engine/test_train_inference_consistency.py`：
- 构造 5 个 case → 训练 → 加载权重 → 推理 → 验证特征 keys 一致
- 验证权重热加载无 side-effect

**验收**：CI 通过，覆盖权重切换路径。

---

## 五、阶段 C：库存历史采集（P0 · 持续运行）

### C1 · 每日库存快照采集器

**问题**：库存信号用当前快照，无历史，无法回测、无法做"库存趋势"分析。

**方案**：

新建 `src/data/inventory_snapshot.py`：
- `collect_snapshot(good_id) -> dict`：调 `/monitor/get_good_rank` + `/monitor/get_task_trends`，返回结构化快照
- `save_snapshot(snapshot, date, cache_root)`：落盘到 `data/inventory/{good_id}/{YYYYMMDD}.parquet`
- `load_snapshots(good_id, start, end) -> DataFrame`：加载区间快照

新增调度入口 `scripts/collect_inventory_daily.py`：
- 从 watchlist（见阶段 E）拉取品列表
- 逐品采集快照并落盘
- 受 1 req/s 限流，预期 50 品 × 2 接口 = 100s

**部署**：systemd timer 或 cron，每日 03:00 执行（避开交易活跃期）

**验收**：
- 跑一次 → `data/inventory/{good_id}/` 出现当日 parquet
- `load_snapshots(good_id, "2026-08-01", "2026-08-31")` 返回 DataFrame

---

### C2 · 库存快照 schema

```python
{
    "good_id": str,
    "date": "YYYYMMDD",
    "holders": [{steam_id, hold_count, hold_value, ...}],  # top-N
    "trends": [{type, count, time, steam_id, ...}],       # 近 7 日
    "computed_signals": {                                  # 即时算好
        "top3_concentration": float,
        "net_inflow_7d": float,
        "active_ratio": float,
        "inventory_score": float,
    },
    "collected_at": ISO8601,
}
```

**决策**：快照只存原始数据 + 即时算分，**不存历史 trends 全量**（避免数据爆炸），trends 仅保留当日采集到的窗口。

---

### C3 · 采集监控

**交付物**：
- `/inventory/snapshot-status` 端点：返回最近 7 日采集成功率、缺失品列表
- 前端 MonitoringPage 增加"库存采集"看板

**验收**：连续 7 日采集成功率 ≥ 95%，缺失品可在 UI 看到。

## 六、阶段 D：双轨融合训练 + 案例飞轮（P1）

### D1 · 案例库纳入库存特征

**问题**：[training_endpoints.py:234](file:///workspace/src/api/training_endpoints.py#L234-L247) 构建案例只调 `detect_accumulation`，无库存特征 → 训练实为单轨。

**方案**：

1. `build-cases` 端点改为：对每个 case 时点，加载该日的库存快照（来自阶段 C），调 `compute_inventory_signals`，写入 `inventory_score` / `inventory_signals`
2. 案例 schema 增加 `inventory_features` 字段
3. `trainer.py` 的 `FEATURE_KEYS` 扩展为 K 线 + 库存双轨特征向量
4. 训练 LogisticRegression 拟合双轨特征 → 真正的"双轨融合训练"

**依赖**：阶段 C 已积累 ≥90 天库存快照

**验收**：
- 案例库 JSONL 单条记录含 `inventory_score` 字段
- 训练产物权重表包含库存特征（concentration / net_inflow / activity / synergy）
- 训练准确率 > 单轨基线

---

### D2 · 实时分析自动入案例库

**问题**：训练→推理→新案例→再训练的飞轮未启动。

**方案**：

1. `/accumulation/analyze-fused` 端点在返回结果前，异步写一条 case 到 `data/cases/rifle_cases.jsonl`
2. case 含完整双轨特征 + 时间戳，label=None（待标注）
3. 用 `asyncio.create_task` 非阻塞，分析响应不被拖慢

**交付物**：
- `case_store.py` 新增 `save_case_async()`
- accumulation_endpoints.py 在返回前调用

**验收**：分析 5 个品 → 案例库新增 5 条，label=None

---

### D3 · 事后标注自动化

**问题**：当前标注需手动触发 `label-cases`。

**方案**：

1. 每日采集库存快照后，触发 `label_cases_with_horizon` 对到期的未标注 case（即创建满 30 天的）
2. 标注后自动写回 JSONL + Parquet

**部署**：与 C1 同一个 systemd timer 串联执行

**验收**：连续运行 30 天后，自动开始有 labeled 案例。

---

### D4 · 增量训练调度

**问题**：训练需手动触发。

**方案**：

1. 每周日凌晨触发 `/training/train`（标注后）
2. 训练完成后自动刷新 detect_accumulation 的权重缓存（B2 的 mtime 检测）
3. 训练产物增加版本号 + 训练时间，前端可看历史版本

**验收**：每周一查看训练产物 mtime 更新，在线分析 weights_source=trained。

## 七、阶段 E：侦察告警机制（P1）

### E1 · watchlist 订阅

**问题**：产品叫"侦察兵"但无侦察机制，用户必须主动查。

**方案**：

1. 新建 `data/watchlist.json`：用户关注的品列表
2. 前端 AccumulationPage 增加"加入关注"按钮
3. 新端点 `POST /watchlist/add`、`GET /watchlist/list`、`DELETE /watchlist/{good_id}`

**验收**：UI 可加入/移除关注品，列表持久化。

---

### E2 · 阈值告警触发

**问题**：无主动通知。

**方案**：

1. 每日库存采集 + 双轨分析后，对 watchlist 内每个品计算融合评分
2. 评分突破阈值（默认 ≥0.6 或较前日上升 ≥0.15）→ 触发告警
3. 告警落盘 `data/alerts/{YYYYMMDD}.jsonl`

**告警内容**：
```python
{
    "good_id": str,
    "good_name": str,
    "fused_score": float,
    "prev_score": float,
    "delta": float,
    "pattern": str,
    "evidence": [str],
    "triggered_at": ISO8601,
}
```

**验收**：watchlist 内某品评分突破 → alerts 目录出现记录。

---

### E3 · 告警通知通道

**方案**（单用户场景，轻量）：
- 默认：写入 `data/alerts/` + 前端 AlertsPage 红点提示
- 可选：webhook（飞书/钉钉机器人）通过环境变量 `ALERT_WEBHOOK_URL` 配置

**验收**：配置 webhook 后，告警触发 → 收到推送。

## 八、阶段 F：质量优化（P2）

### F1 · 标签规则升级

**现状**：仅用 30 天涨幅 ±15%/−10% 判定，忽略回撤。

**升级**：
- 正样本：30 天涨幅 ≥ 15% **且** 最大回撤 ≤ 8%（可持有体验）
- 负样本：30 天跌幅 ≥ 10% **或** 最大回撤 ≥ 15%（止损触发）
- 引入"持有期收益"标签（不止看终点）

**验收**：标签分布更均衡，neutral 比例下降。

---

### F2 · 检索特征对齐

**问题**：[case_retriever.py](file:///workspace/src/scenario_engine/case_retriever.py) 只用 K 线 10 维，与融合特征不对齐。

**升级**：检索特征 = K 线 + 库存双轨向量（依赖 D1），hit_rate 改为"预测准确率"（标注正确率）而非"positive 占比"。

---

### F3 · LLM 归因增强

**升级**：
- 相似案例 ≥3 条时才喂 LLM（避免噪声）
- prompt 增加双轨对比结构化模板
- 引入"置信度校准"：LLM 输出的"高/中/低"与历史命中率对齐

---

### F4 · 团队分析异步化

**问题**：[analyze-fused](file:///workspace/src/api/accumulation_endpoints.py#L416-L420) 含团队时 10s+ 响应。

**升级**：
- 团队分析改为异步任务，返回 task_id
- 完成后写入 `_TEAM_CACHE`，下次分析自动命中
- 前端先显示 K 线 + 库存，团队评分"计算中..."

## 十一、关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `/info/chart` 所有平台都只给收盘价 | A1 失败 | 降级 CLOSE_ONLY 模式，K 线轨诚实降级 |
| 库存采集被 CSQAQ 限流封禁 | C 失败 | 1 req/s 严守 + 错峰采集 + 失败重试 |
| 训练样本不足导致权重不收敛 | B 失败 | 保留 empirical 兜底，训练产物标记 `trained=False` |
| LLM API 不稳定 | LLM 归因失效 | 已有模板降级，不影响核心判断 |
| 库存快照存储爆炸 | C 数据膨胀 | 只存 top-N holders + 当日 trends 窗口，单品单日 <100KB |

---

## 十二、不做的事（明确边界）

为避免范围蔓延，以下事项**本阶段不做**：

1. ❌ 多用户/账号体系（用户明确"一个人用"）
2. ❌ 自动交易/下单（仅识别不操作）
3. ❌ 第三方数据源接入（只用 CSQAQ）
4. ❌ 复杂 ML 模型（保持 LogisticRegression 可解释性）
5. ❌ 实时推送（每日批量足够，避免实时性带来的复杂度）
